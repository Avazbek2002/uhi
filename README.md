# Heat Atlas / Tashkent

A static React + TypeScript decision-support dashboard for exploring urban heat exposure across Tashkent mahallas and districts. The interface keeps thermal values visually prominent, exposes low-confidence observations, and calculates district rollups in the browser.

## Run locally

```bash
npm install
npm run dev
```

The dashboard works without a Mapbox token: it uses an SVG renderer over the supplied WGS84 boundaries. To enable the Mapbox GL JS basemap and interaction layer, create `.env.local`:

```bash
VITE_MAPBOX_TOKEN=pk.your_public_token_here
```

### Continuous Landsat LST overlay

The mahalla GeoJSON files are boundaries and zonal summaries; they do not contain the continuous 30 m LST surface. To display the actual pixel-level Landsat product over the whole city, provide a **manifest URL** in `.env.local`:

```bash
# Cloudflare R2 public endpoint hosting the scene manifest.
# The manifest is generated by the backend upload script after each run.
VITE_LST_MANIFEST_URL=https://pub-ec33c8a1d13f40f4935fa09d39bb00ce.r2.dev/landsat-lst-scenes/maps_manifest.json
```

The manifest is a JSON file with a `maps` array containing available acquisition dates and their PNG visualization URLs:

```json
{
  "maps": [
    {
      "date": "2024-06-04",
      "url": "https://pub-ec33c8a1d13f40f4935fa09d39bb00ce.r2.dev/landsat-lst-scenes/tashkent_2024-06-04.png",
      "label": "Landsat acquisition"
    }
  ]
}
```

The calendar UI displays available dates based on this manifest. When a user selects a date, the frontend fetches the corresponding PNG and overlays it on the map. PNGs are pre-rendered with transparent non-data pixels and a thermal color ramp, so they display directly without client-side processing.

**📖 Complete integration guide:** See [`LST_R2_INTEGRATION.md`](./LST_R2_INTEGRATION.md) for the full pipeline architecture, troubleshooting, and R2 bucket configuration.

#### Alternative raster sources

For local development or static deployments without R2, you can also use:

```bash
# A georeferenced PNG/JPEG covering Tashkent. The default image bounds are
# 69.08E to 69.45E and 41.20N to 41.42N.
VITE_LST_RASTER_URL=/data/tashkent_lst_summer_2024.png

# Or a tiled raster endpoint backed by a COG/GeoTIFF service.
VITE_LST_RASTER_TILE_URL=https://your-tile-service/{z}/{x}/{y}.png

# Or a direct GeoTIFF URL (parsed in-browser — use tiles for large files).
VITE_LST_GEOTIFF_URL=https://data.example.com/tashkent_lst_summer_2024.tif
```

Use only **one** raster source. The manifest URL takes priority when set. All remote resources must allow CORS reads from your frontend domain.

Build and preview the static bundle with:

```bash
npm run build
npm run preview
```

## Data files

Place production assets in `public/data/`:

| File | Required fields |
| --- | --- |
| `tashkent_mahallas_master.geojson` | `mahalla_id`, `mahalla_name`, `district_id`, `population`, `employment`, `geometry` |
| `tashkent_districts_master.geojson` | `d_id`, `geometry` |
| `mahalla_lst_stats_mahalla.geojson` | `mahalla_id`, `lst_mean`, `lst_std`, `lst_min`, `lst_max`, `lst_count`, `low_confidence` |

All files must be WGS84 GeoJSON. Mahalla and stats rows are joined by `mahalla_id`. The current repository includes the two master boundary files and copies them into `public/data/` during setup. If the LST stats file is missing, the app generates deterministic demo LST values from the source `composite_value` field so the product remains explorable during development. The demo values are clearly a fallback for local UI work, not an analysis dataset.

## Zonal-statistics pipeline

1. Prepare a summer Landsat thermal composite and the downscaled 30 m LST raster in a projected CRS suitable for the analysis area.
2. Reproject the mahalla boundaries to the raster CRS.
3. Mask the raster by each mahalla polygon and calculate mean, standard deviation, minimum, maximum, and valid pixel count.
4. Set `low_confidence` to `true` when `lst_count < 50`. Do not filter these rows out.
5. Reproject the output boundaries back to WGS84 and write `public/data/mahalla_lst_stats_mahalla.geojson`.

Example Python stack for a custom pipeline:

```bash
pip install geopandas rasterio numpy shapely
```

The browser computes district metrics from the resulting mahalla rows. Population-weighted means use `population` as the weight; the unweighted average is retained for analysis extensions. No district CSV is required.

## Deploy to Vercel

Import the repository into Vercel with the following settings:

- Framework preset: `Vite`
- Build command: `npm run build`
- Output directory: `dist`
- Environment variable: `VITE_MAPBOX_TOKEN` (optional when using the SVG fallback)

Because all data is fetched from `public/data/`, the generated site is fully static and can also be deployed to Netlify or GitHub Pages. For GitHub Pages under a repository subpath, set the Vite `base` option to the repository name before building.

## Product notes

The map color scale is reserved for mean LST. Population is shown as its own sortable column rather than blended into a composite score. Mahallas with fewer than 50 valid interior pixels remain visible with reduced opacity and a hatched overlay, and the methodology panel explains how to interpret them.
